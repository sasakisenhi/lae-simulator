# Design

## Context

動機と範囲はproposal.mdを参照。現リポジトリにはOpenSpec設定だけがあり、既存のソース、テスト、依存関係、入出力契約はない。Python 3.14.8とNode.js 24.16.0の存在は読み取り確認済み。正式なLAE資料は未提供であり、以下の業務規則は実証用の提案であって、実企業やLAEの確定設定ではない。

## Goals / Non-Goals

**Goals:** 小さなローカル実行で、入力固定から業務実行、記録・経験形成、境界検査まで縦断できる。後続機能は保存済み結果を利用できる。

**Non-Goals:** 分散実行、マルチユーザー認証、実際のGit/CI連携、LLM実行、高度な認知、介入比較の実装。拡張性は明示した責務と版管理で確保し、汎用プラグイン基盤は作らない。

## Decisions

### D1. 小規模なローカルプログラムとして構成する

対応要件: `world-definition/Explicit world inputs`、`simulation-execution/Reproducible execution`。

初期案はPython 3.14系、標準ライブラリ中心のパッケージとCLI、標準のテスト機能とする。Pythonは構造化データ、優先度キュー、検証の実装を少ない依存で行える。TypeScriptも成立するが既存Web実装がなく、現時点でWeb向け統合の利益はない。専用シミュレーションフレームワークは初期の規則と再現条件を隠さないため採用しない。言語は外部要件ではなく、交換可能な実装判断である。

対象は単一端末の管理者実行。入力検証、実行、出力、検査のCLI入口を設ける。コマンドの綴りや内部クラス階層は固定しない。正準ファイルを直接読めるOS利用者からの秘匿は保証しない。調査者へは投影出力だけを配布する運用を明示する。

### D2. DESを実行基盤にし、社員の判断は明示的な規則とする

対応要件: `simulation-execution/Code change lifecycle`、`Explainable background influence`、`Knowledge bounded decisions`。

イベント時刻順に状態を進め、社員・CIの空き資源と作業待ち行列を扱う。初期規則は担当割当、着手、レビュー依頼先の選択、修正、CI再実行、マージを対象とする。社員判断の入力には本人の役割・利用可能な連絡・自分の作業状態だけを渡し、資源競合やCI判定などの環境処理はエンジンが行う。判断が参照した知識の根拠を管理用履歴に残す。

社員が一度に行う能動作業は1件とし、複数の待機中Issueは保持可能。CIは別の有限資源。レビュー承認とCI成功が揃えばマージでき、修正要求は実装工程へ戻る。マージ時にIssueの中心工程を完了とする。QA差し戻しは元Issue/PRに関連づけた新しい修正Issueを投入し、マージ済み履歴を書き換えない。企画変更は未完了作業の必要量を変更、依存は待機・解除、割り込みは進行中作業の残量を保存して一時停止・再開する。全作業の期間内完了は要求せず、終了時の未完了状態も保存する。

背景イベントは事前定義または固定規則から生成し、理由・作用・通知内容を区別する。業務規則による確率的な修正や失敗は許容するが、課題発生を保証するための結果選別は行わない。テスト用の確定的失敗条件は、試験目的と明示して通常ケースと分ける。

ABMは社員の学習や複雑な相互作用が必要になれば再検討する。LLMによる実行中判断は再現性と知識境界を複雑にするため今回導入しない。

### D3. 論理時間と乱数の扱いを明示する

対応要件: `world-definition/Predetermined study timeline`、`simulation-execution/Reproducible execution`、`Execution provenance`。

開始日時と業務カレンダーを入力し、内部は開始からの整数分で表す。12週は連続した84日、各期は半開区間の28日とする。社員の稼働時間・休日はカレンダーで定義し、業務期間の時計と区別する。同時刻イベントは明示した優先順位と決定的な投入連番で処理する。実時間、集合の反復順序、ランダムUUIDを業務結果へ混入させない。

シードから安定した方法で用途別の乱数列を導出し、少なくとも外部入力・作業量・レビュー/CI結果を分ける。Python組み込みhashによる導出は使わない。これは将来の比較を阻害しにくくする措置であり、共通シードだけで介入間の比較可能性を保証しない。

保証は同じ入力、エンジン・定義版、固定ランタイム/依存版での論理的再現。manifestにOS、ランタイム、依存版、エンジン版を記録し、異環境の完全一致は未検証とする。実時間等の管理情報を除いた意味内容を正規化して比較する。

### D4. 正準状態と二種類の投影を分ける

対応要件: `evidence-projection/Shared evidence origin`、`Employee perception boundary`、`Fixed employee evidence package`、`simulation-execution/Consistent canonical history`。

論理コンポーネントはWorld Loader、Simulation Engine、Projector、Run Store、Validator。別サービスには分割しない。

```text
World Loader --> frozen world + run conditions
                         |
                         v
                 Simulation Engine
                         |
                         v
              canonical events + final state
                         |
                         v
                      Projector
                         |
                +--------+--------+
                v                 v
          work records      employee experiences
                |                 |
                +--------+--------+
                         v
                 Validator / Run Store
                         |
                         v
                 role-scoped exports
```

保存上の最小の意味契約は次のとおり。網羅的なフィールドや継承階層は固定しない。

| 情報 | 必要な意味 |
|---|---|
| 世界入力 | 定義版、検証用/正式の区別、社員と背景知識、規則、初期状態、カレンダー、公開・保存条件 |
| 実行識別情報 | 入力スナップショットの識別値、シード、期間、エンジン/環境版、結果状態 |
| 正準イベント | 実行内の安定したID、時刻・順序、種類、主体・対象、状態変化、因果参照、通知・知覚範囲 |
| 業務記録 | 業務側ID、対象、時刻、記録内容、閲覧範囲、保存条件 |
| 社員経験 | 社員、知覚時刻、経験内容、直接経験/伝聞、根拠参照 |
| 管理用対応表 | 投影IDからイベント/背景情報への参照、投影版 |

規則・望ましい状態、実際のイベント、派生した記録・経験、検査結果を別に保持する。知覚した伝聞は世界の真実と一致しなくてもよい。現変更は誤認を積極的に生成する機構を持たないが、伝えられた内容と実際の原因を別に保持する。正準情報から本人向け情報を生成するとき、管理用根拠が本文に混入しないよう分離する。

後続の記憶・認識形成は固定社員情報と知覚履歴を入力とし、その成果物は新しい版の派生情報になる。LLM回答が正準イベントを追加する経路は設けない。

### D5. 可読なファイルで保存し、完了時に公開する

対応要件: `world-definition/Identifiable frozen inputs`、`simulation-execution/Frozen completed run`、`Explicit failed execution`。

初期案は入力/manifest/最終状態をJSON、イベント・記録・経験をJSON Linesで保存する。SQLiteは検索件数と利用形態が明らかになってから導入可能。完全なイベントソーシングDBや復旧機構は作らず、履歴と最終スナップショットを併用する。

実行結果は新規の実行ディレクトリへ出し、既存完了結果の上書きを拒否する。Run Storeは一時領域へ保存し、Validatorが状態遷移・参照・資源・時刻・投影根拠を検査してから完了を公開する。読み取り側は明示的な完了表示がない結果を利用しない。途中障害は非正常結果または未完了一時領域として扱い、CLIは非成功終了を返す。自動再試行、障害からの再開、ストレージ破損の自動修復は扱わない。

入力不正はLoader、遷移不正はEngine/Validator、根拠不正はProjector/Validator、保存不正はRun Storeが検出する。オーケストレーターは正常公開を停止し、管理者へ対象と理由を返す。既存成功結果へフォールバックして今回の成功と見せない。

### D6. 出力時に公開境界を適用する

対応要件: `evidence-projection/Role bounded disclosure`、`Retention bounded historical access`。

正準保存領域と公開用出力先を分離する。Projector/出力処理は許可項目だけを構成し、調査者へ内部パラメータや非公開根拠を出さない。社員本人向け情報は将来の回答生成側へ渡すためのもので、調査者に社員の内的記憶を丸ごと開示する意味ではない。

権限は呼出側の明示した役割・対象社員に対して判定し、不明な役割は拒否する。これは認証を持つサービスではなく、信頼された管理者が適切な成果物を配布する境界である。未許可情報の存在が分かるエラーを調査者へ返さない。

保存期限は第12週終了時点で評価し、主観測期間とは独立する。情報源ごとの保存期間を定義し、許可された12週内の古い記録も出力する。正準履歴は管理者向け監査資料として保持できるが、業務側で失われた記録の代用品として調査者に出さない。

この公開境界は後続のヒアリングにも影響する高影響の契約。変更時は権限別の漏洩検査と利用側の再検証を必要とする。

### D7. 初期機能と検証証拠を縦断で揃える

対応要件: 三capabilityの全要件、特に`evidence-projection/Projection consistency report`。

最初の完成単位は、検証用世界の読み込みからIssue/PR業務を実行し、共通イベントから記録と社員経験を保存・検査できること。CLIと自動テストで確認し、GUIは不要。

検証世界には少なくとも開発担当2人、レビュー可能な社員、CI資源を置き、複数Issueの競合と非公開背景イベントを試せるようにする。QA等の関係者は通知元として定義でき、詳細な作業主体にはしない。規模や人数はLAE設定の確定ではない。

テストは正常フロー、修正、CI失敗、背景四種、同時刻、社員間の知覚差、保存期限、参照切れ、不正遷移、根拠偽造、保存中断を含む。同一条件の独立プロセス2回で正準列・状態・投影内容が一致することを確認する。別シードで必ず結果が異なるとは要求せず、シードが記録され、確率的規則に使われることを確認する。

報告は機械検査可能な項目のPASS/FAILと、本変更では判定不能なUNKNOWN/対象外を区別する。これによりLLM発言の妥当性やDevEx改善効果まで検証済みと誤認させない。初期基盤の整合性は実企業らしさの証明ではなく、小規模モデルの十分性は未検証のまま実行結果と限界を報告する。

### D8. 将来介入への制約は版と履歴に残す

対応要件: `simulation-execution/Frozen completed run`、`Execution provenance`、ユーザーの介入方針。

ベースラインは保存済み入力・履歴を変更しない。介入は別入力/規則版/実行として扱えるよう入力識別を維持する。モデル拡張が必要な場合、変更点と追加仮定、どのベースラインが同じモデルで再評価可能かを後続変更で記録する。旧履歴の書き換えはしない。効果がモデルに表現されないとき、代理指標から効果を捏造しない。介入API、共通乱数の対応付け、効果量の算出は今回作らない。

## Risks / Trade-offs

- [規則が粗く、調査に必要な違いが生じない] → 基盤の整合性とケーススタディ成立性を分け、後続の小規模調査で粒度を評価する。問題が出るシードの事後選別はしない。
- [正準原因と社員認識の混同] → 通知内容・知覚範囲・管理用根拠を分け、異なる社員への投影を比較する。
- [ファイル構造に将来機能が依存する] → 意味契約と版を明示し、保存方式を内部境界に閉じる。全版互換の移行基盤は先取りしない。
- [シードが同じなら異モデルも公平に比較できるとの誤認] → 対応環境とモデル版を記録し、比較可能性は後続の介入評価側で判定する。
- [管理者権限による秘匿破り] → 初期の配布運用を明記する。OSアクセスまで防ぐ認証・隔離は後続要件が生じた時点で設計する。

## Migration Plan

新規機能で既存データ移行はない。検証用世界で入出力契約とテストを揃えてから、正式資料の取り込みを別変更として行う。実装撤回時も保存済み結果は削除・上書きせず、利用したエンジン版を保持する。契約改訂時は旧結果をそのまま識別可能にし、旧版を自動変換して再現できた扱いにはしない。

## Open Questions

- 正式なLAE資料における人数、業務カレンダー、タスク量と分布値。初期は明示的な検証値を用い、正式資料受領時に検証する。
- 後続の記憶・認識形成、自由質問回答、介入評価の具体方式。今回の固定履歴と知覚境界を入力契約とし、それぞれ別変更で設計する。
