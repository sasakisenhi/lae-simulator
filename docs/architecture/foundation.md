# 再現可能なシミュレーション基盤の技術選定

本書はOpenSpec変更 `build-reproducible-simulation-foundation` のTask 1.1で固定した実装方針である。Task 1.2で入力契約とCF0を追加し、Task 1.3でこの方針に沿う最小の実行・再生・保存・公開投影を実装した。

## 選定

### 言語と実行環境

Python 3.14.8を採用する。`dataclass`、型注釈、列挙型、標準JSON、`heapq`、`unittest`で、状態・イベント・reducer・決定的キューを外部フレームワークなしに明示できるためである。MVPは単一端末のローカル処理であり、Webサービス、DB、非同期I/O基盤は置かない。

`.python-version` と `pyproject.toml` がpatch版まで固定し、`uv.lock` がプロジェクトの解決結果を固定する。ビルドバックエンドは `pyproject.toml` で完全版を固定し、実行時依存とテスト依存はゼロである。uv 0.12系の `uv sync --locked` をクリーン環境の標準入口とし、lockfileと宣言が不一致なら更新せず失敗させる。

### イベントキュー

標準ライブラリの `heapq` を用いる。専用DESライブラリは導入しない。キュー項目の比較キーは次の固定tupleとする。

```text
(due_tick, priority, insertion_sequence, event_id)
```

- `due_tick` は入力が単位を宣言する非負整数であり、実時間や浮動小数点時刻を使わない。
- `priority` はDesign D5の分類値（10、20、30、40、90）を使う。
- `insertion_sequence` はrun内で単調増加する整数で、同時刻・同分類の安定投入順を固定する。
- `event_id` は検査と明確な全順序のために含め、ランダムUUIDや処理系依存hashから生成しない。

小さいpriorityのイベントを処理中の同一tickへ遡及投入しない。必要なら次tickへ送る。Task 1.3は予約・消費を正準イベントとして記録し、キューをその履歴から導出する。取消・失効は後続タスクで同じ契約へ追加する。したがって、利用ライブラリの内部順序を再現性の根拠にしない。

### 保存形式と正規化

物理保存にはUTF-8のJSONとJSON Linesを採用する。Task 1.3では各runを新規ディレクトリへ固定し、manifestに各artifactのSHA-256を記録する。

- JSON: manifest、固定入力、初期スナップショット、派生状態、検査結果など一つの値として検証する成果物。
- JSON Lines: 追記順そのものに意味がある正準イベント列。1行を1イベントとし、論理順序を配列やファイル列挙順へ暗黙委譲しない。
- テキストはBOMなしUTF-8、改行はLF、末尾改行あり。
- object keyはUnicodeコードポイント順に並べ、空白を挿入しない。文字列はUnicodeとして保持する。
- 論理時間、順序、版番号は整数で表す。NaN、Infinity、浮動小数点時刻、日時のローカルタイム表現を正準データへ入れない。
- 内容識別値は正規化済みbytesへSHA-256を適用し、アルゴリズム名とともにmanifestへ記録する。

JSONは言語固有オブジェクトの永続化より目視・差分・別実装での検査が容易で、SQLiteや外部DBなしで固定runを新規ディレクトリへ保存できる。Task 1.3でschema 1.0と、検査済み一時ディレクトリを新規runディレクトリへrenameする公開手順を実装した。

## 再現性と再生の契約

権威ある再生入力は、固定入力と規則 `I`、初期スナップショット `S0`、順序付き正準イベント列 `L` である。最終状態、キュー、Workspace、本人の知覚、公開投影は派生物として扱い、次式の結果と照合する。

```text
S_n = fold(reduce, S0, L[1..n], I)
```

通常実行と再生は同じ純粋なreducerを使う。reducerは入力状態を変更せず、新しい状態を返す。再生はPolicyを再実行せず、乱数、壁時計、ネットワーク、環境変数、ファイル列挙順を参照しない。状態差分を無検査で適用せず、イベント種別ごとの前提、版、権限、許可された効果を検証する。

manifestには少なくとも入力・規則・エンジン・ランタイム・lockfileの識別値、OS情報、時間単位、期限、シード、正規化規則版を保存する。シードは再現条件の一部だが、Task 1.1では乱数方式を実装しない。主たる決定的試験では乱数を使わない。

## 役割別公開上限

公開上限はコード側の閉じた役割定義として実装し、教材やrun設定は上限を狭めることだけを許す。設定allowlistとの積集合を入力検査時と出力時の両方で評価し、未知の役割、未知の分類、上限を広げる設定はfail closedで拒否する。

固定する役割は次の4種である。

| 役割 | 最大範囲 | 常に除外する範囲 |
|---|---|---|
| administrator | 固定入力、正準履歴、再生状態、検査記録 | 調査セッションへの自動引継ぎ |
| actor-policy | 当該時刻までの本人の知識・知覚・予測 | 管理用正解、隠れた原因、未観測の予約payloadと実未来時刻 |
| interview-generator | 固定本人パッケージ中の回答可能かつ開示可能な情報 | 他者だけの知識、失われた記憶の復元、管理用原因・正解、未観測未来 |
| investigator | 許可された操作ログ・資料・回答・公開関連ID | 管理用真因・正解経路、非公開予約、私的根拠ID・規則閾値 |

本人の認識は世界の真の状態と別の型・保存区画に置き、投影時に暗黙結合しない。エラー本文、件数、ID、関連先にも同じ上限を適用する。具体的な型と検査はTask 1.2以降で実装する。

## 境界と後続作業

Task 1.1の `doctor` は固定ランタイムと入口の確認だけを行う。Task 1.2の `validate-world` は入力を検証するが、候補選択や状態変化を行わない。Task 1.3の `run` と `public-log` は、企業設定と実在Issueから独立したCF0を、汎用Policy、決定的キュー、同一reducer、固定Store、fail-closed Projectorへ接続する。

Task 1.3の状態は、論理時刻、Workspace入力版、本人の知識ID、表示対象、候補の選択・完了、予約キュー、消費済み予約、業務終了状態、内部有効性を持つ。正準履歴は状態外の追記順イベント列であり、通常実行と再生が同じreducerを使用する。AI、変更、チェック、協働、中断・再開は実装しておらず、後続タスクで同じ契約を拡張する。

## アーキテクチャ原則

本基盤は単一プロセスのモジュラーモノリスとして保ち、パターン名への形式的一致ではなく次の性質を維持する。

- 状態遷移、検証、Policy、Projectionは決定的なcoreへ置き、CLI、ファイルシステム、外部SDK、ネットワーク等の副作用は薄いshellまたは境界adapterへ隔離する。
- Domain CoreはCLI、外部SDK、特定の保存・ファイルシステム実装へ依存しない。外部I/Oを置換してもWorldの意味、状態遷移規則、正準イベントと再生結果が変わらない依存方向にする。必要な境界だけをportとして扱い、抽象クラスやDIフレームワークを一律に設けない。
- World、Policy、Scenario、Issue固有の候補・規則はデータ駆動で定義し、汎用engineへ識別子固有の分岐を追加しない。
- 正準イベント履歴を派生状態の根拠とし、通常実行と再生で同じreducerを用いる。保存状態、本人情報、公開記録は正準履歴との一致を検査する。
- 管理用、本人用、調査者用等のProjectionは役割別に明示して分離する。公開Projectionは管理用真因、正解経路、未観測未来を参照せずに成立させる。
- ドメイン用語と不変条件の所有者を明確にする。engineは調停、reducerは状態遷移、Storeは物理保存、Projectorは情報上限を適用した派生に責任を持つ。

先行して汎用イベントレジストリ、別DB、サービス分割、全境界のinterface化を導入しない。機能追加で責務または変更理由が実際に分かれた時点で、公開API、固定入力、正準履歴、保存形式の互換性を保ちながら局所的に分割する。

## Python patch版更新時の再検証

セキュリティ修正等でPythonのpatch版を更新する場合は、`.python-version`、`pyproject.toml`、`uv.lock`、CLIの`SUPPORTED_PYTHON`を同じ変更で更新する。そのうえで、隔離環境での`doctor`、全自動テスト、`compileall`、CF0の検証と内容識別値、JSONの正規化結果、OpenSpec strict validationを再確認する。標準ライブラリのJSON・列挙型・dataclass・hashlibの挙動差と、ビルドバックエンドの対応状況も確認する。確認前に旧patch版の結果と新patch版の結果を同一対応環境の証拠として扱わない。
